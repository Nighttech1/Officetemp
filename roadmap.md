# Пошаговый план разработки MVP SaaS-платформы генерации документов

Данный roadmap разбит на логические фазы. Мы начинаем с создания отказоустойчивого ядра и решения самых сложных алгоритмических проблем, а затем наращиваем пользовательский интерфейс и интеграции.

## Фаза 1: Фундамент и Инфраструктура
*Цель: Развернуть защищенное ядро системы и подготовить базу данных.*

- [x] **1.1. Настройка окружения:** Инициализация проекта FastAPI + PostgreSQL. Настройка Docker Compose для локальной разработки.
- [x] **1.2. Проектирование БД:** Создание таблиц `Users`, `Organizations` (для изоляции tenant-ов по 152-ФЗ), `Templates` и `GenerationLogs`.
- [x] **1.3. Авторизация и безопасность:** Реализация JWT-аутентификации. Настройка системы прав доступа (RBAC).
- [x] **1.4. Хранилище файлов:** Настройка S3-совместимого хранилища (например, Yandex Object Storage) для безопасного хранения шаблонов и временного хранения готовых документов.

## Фаза 2: Ядро генерации документов (Doc Engine)
*Цель: Решить главные "боли" — сохранение сложной верстки и динамические таблицы.*

- [x] **2.1. Базовый парсер DOCX:** Интеграция `docxtpl`. Написание сервиса для замены плоских текстовых тегов (например, `{{ ClientName }}`).
- [x] **2.2. Умные динамические таблицы:** Реализация логики обработки циклов `{% tr for %}`. Написание unit-тестов с загрузкой сложных юридических договоров для проверки сохранения нумерации и отступов.
- [x] **2.3. Микросервис PDF-конвертации:** Offline OSS **dxpdf** (Rust+Skia, MIT) — DOCX→PDF без LibreOffice и без внешних SaaS.
- [x] **2.4. Анализатор шаблонов:** Разработка функции, которая читает загруженный `.docx` и автоматически возвращает список всех найденных в нем тегов (для будущего маппинга на фронтенде).

## Фаза 3: Обработка данных и Интеграции
*Цель: Научить систему получать данные из разных источников (решаем проблему изоляции данных).*

- [x] **3.1. Парсер Excel/CSV:** Реализация загрузки статических файлов с реестрами (например, выгрузка из 1С). Конвертация данных в массивы JSON для движка генерации.
- [x] **3.2. Коннектор Google Sheets:** Настройка OAuth/Service API для подключения облачных таблиц Google.
- [x] **3.3. Коннектор Яндекс Таблиц:** Интеграция API Яндекса (особенно важно для российского рынка после 152-ФЗ).
- [x] **3.4. Агрегатор данных:** Единый интерфейс нормализации данных. Любой источник (Excel, Google, Яндекс) должен на выходе давать стандартизированный JSON.

## Фаза 4: Пользовательский интерфейс (Frontend)
*Цель: Создать интуитивно понятный No-code кабинет пользователя.*

- [x] **4.1. Авторизация и ЛК:** Экраны регистрации, входа и управления профилем компании.
- [x] **4.2. Библиотека шаблонов:** Раздел для загрузки файлов Word, предпросмотра и управления версиями шаблонов.
- [x] **4.3. Интерфейс маппинга (Visual Mapper):** Экран, где пользователь связывает колонки из загруженной таблицы с тегами, найденными в Word-шаблоне (UI drag-and-drop или выпадающие списки).
- [x] **4.4. Дашборд генерации:** Экран статуса генерации с прогресс-баром и кнопкой "Скачать ZIP архив" / "Скачать PDF".
 - [x] **4.5. Frontend Asset Pipeline:** Внедрить конвертацию изображений в AVIF/WebP, генерацию постеров для видео и blurhash для placeholder'ов.

## Фаза 5: High-load, Масштабирование и Релиз
*Цель: Подготовка платформы к пиковым нагрузкам (сотни документов в минуту) и запуск.*

- [x] **5.1. Очереди задач (Celery):** Перевод функции генерации из синхронного режима в фоновый асинхронный с использованием Celery + Redis.
- [x] **5.2. Сборка ZIP-архивов:** Логика автоматической упаковки сотен готовых файлов в один архив для удобного скачивания.
- [x] **5.3. Автоочистка данных:** Написание скрипта по удалению готовых документов и кэша данных с серверов через 24 часа (требование комплаенса и экономии места).
- [x] **5.4. Нагрузочное тестирование:** Проверка системы на генерации 1000+ сертификатов одновременно.
- [x] **5.5. Релиз MVP:** Пакет релиза готов (`docs/RELEASE.md`, compose release overlay). **VPS / production — ожидает согласования Клиента (явное «да»); автодеплой не выполняется.**
- [x] **5.6. Интеграция Playwright E2E:** Настроить автозапуск стабильных E2E-тестов в CI/CD.
- [x] **5.7. Глубокий аудит доступности (Accessibility):** Проверить контраст, клавиатурную навигацию и ARIA.
- [x] **5.8. Обработка форм и email:** Внедрить маршруты приема форм, антиспам и безопасную загрузку файлов.

## Фаза 6: Доработка бэкенда к облачному ЛК и VPS (Postgres + ПДн + документы)

### 6.2. Личный кабинет и персональные данные (152-ФЗ)

- [x] **6.2.4.** Право субъекта: API **удаления/обезличения** ПДн (erase) + запись в `access_audit`.

### 6.3. Проекты, папки, документы на сервере
- [x] **6.3.1.** Убедиться, что snapshot workspace стабильно пишет/читает проекты, папки, карточки документов, подписи (org-scoped).
- [x] **6.3.2.** Убрать/сгладить ошибки конфликта snapshot (422 и т.п.): ревизии, идемпотентность, понятные ответы клиенту.
- [x] **6.3.3.** Непрерывный sync (не только при логине): сохранение дерева после изменений на клиенте → сервер.
- [x] **6.3.4.** Бинарники шаблонов Word (и нужные вложения) → **диск VPS / local volume** (`STORAGE_BACKEND=local`, ключи `org/{id}/…`); в Postgres только `storage_key` / метаданные. (Опционально позже: MinIO/S3 на том же VPS или Yandex — не обязательно для MVP.)
- [x] **6.3.5.** Исходные PDF ИУЛ: политика «не хранить на сервере» или отдельное опциональное хранилище — явно зафиксировать и реализовать.
- [x] **6.3.6.** Фронт/API: после логина с другого браузера/ПК видны проекты, папки, карточки **и** файлы шаблонов (E2E-критерий: `tests/test_second_session_files.py` + гидратация на фронте).
