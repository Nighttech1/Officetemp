# W-35 — Облачный workspace (Postgres + dual-write localStorage) + 152-ФЗ

## Цель (языком Клиента)

Пользователь входит в личный кабинет с любого компьютера/браузера и видит **свои** проекты ИУЛ и накладные, папки, черновики мастеров и библиотеку подписей.  
Данные живут на сервере (PostgreSQL на VPS в России). Браузер дополнительно **копирует** снимок в localStorage «на всякий случай», но источником правды становится сервер.

Исходные PDF чертежей (с которых делают ИУЛ) **не** храним в облаке — только заполненные мастера (как сейчас слева в дереве).

## Уже есть в продукте (не переизобретать)

- PostgreSQL + Alembic, организации (tenants), JWT register/login/me
- `users` без email; email/ФИО в схеме `pii.user_profiles`
- Пароль только `password_hash` (bcrypt/argon через passlib)
- PiiService + AccessAudit
- MinIO/S3-совместимое хранилище для шаблонов

## Чего нет

- API синхронизации `docs-store` (projects/folders/documents/iulWizard)
- API библиотеки подписей
- Dual-write: server ↔ localStorage
- Миграция существующих локальных данных при первом логине
- Явный UI согласия 152-ФЗ + политика под облачный сценарий
- Прод-деплой Postgres на VPS (только после «согласовано» Клиента)

## Пошаговый план разработки (фазы)

### Фаза A — Схема БД и контракт API (localhost)  ← **эта волна начинает здесь**
1. Таблицы public (бизнес, без ПДн в колонках):
   - `workspace_projects` — id, organization_id, owner_user_id, kind, name, client_id (старый id из LS), timestamps
   - `workspace_folders` — дерево папок, organization_id, project_id, parent_id, system_key
   - `workspace_documents` — карточки мастеров; JSONB `wizard` / `iul_wizard`; **без** исходного PDF
   - `signature_folders` / `signatures` — метаданные; картинка → object storage key, не base64 в Postgres
2. RLS / обязательный фильтр `organization_id` на каждом запросе (P0).
3. OpenAPI: `GET/PUT /api/v1/workspace/snapshot`, `POST .../migrate-local`, CRUD подписей.
4. Документ политики хранения (что ПДн / что нет).

### Фаза B — Backend sync + blobs
1. Snapshot pull/push с `updated_at` / revision (last-write-wins на MVP; конфликты → сервер побеждает + toast).
2. Подписи: upload в MinIO/S3 по ключу `org/{org_id}/signatures/{id}.png`.
3. Накладные: шаблон Word / Excel → тот же S3; в JSON мастера только имена/метаданные.
4. **Запрет** эндпоинта загрузки «source PDF для ИУЛ» в workspace.

### Фаза C — Frontend dual-write
1. После логина: `GET snapshot` → записать в localStorage + IndexedDB meta.
2. Любое изменение дерева/мастера: сначала optimistic LS, затем debounce PUT на сервер.
3. Кнопка/авто «Импорт локальных данных» при первом входе (если LS непустой, а сервер пуст).
4. Офлайн: работаем из LS; при появлении сети — sync.

### Фаза D — 152-ФЗ UX и документы
1. Чекбокс согласия при регистрации + ссылка на Политику.
2. Поле `consent_at` уже есть в `user_profiles` — заполнять обязательно.
3. Страницы: Политика конфиденциальности, согласие на обработку ПДн (простым языком).
4. «Удалить аккаунт / выгрузить мои данные» (минимальный MVP endpoint).
5. **Без подтверждения email** на MVP (см. юр. раздел ниже). Опционально фаза E+.

### Фаза E — VPS (только после вердикта Клиента без P0/P1 + явное «да»)

2. TLS, секреты не в репо, бэкапы Postgres, том MinIO.
3. Alembic upgrade + smoke register→sync→второй браузер.
4. Не трогать чужие тома данных без явного запроса пользователя.
5. Пошаговый плейбук деплоя — оформить отдельно (`docs/VPS_POSTGRES_DEPLOY.md`) перед первым продом.
3. Миграции Alembic, smoke register→sync→второй браузер.
4. Не трогать чужие тома данных без явного запроса пользователя.

## 152-ФЗ — ответы для продукта

### Можно ли без подтверждения почты?
**Да, для MVP можно.** Закон 152-ФЗ **не требует** обязательного подтверждения email при регистрации.

Но нужно:
1. **Правовое основание** — согласие субъекта (чекбокс) и/или договор оказания услуг.
2. **Цель** — явно: учётная запись, синхронизация рабочих документов сервиса.
3. **Минимизация** — email, ФИО, hash пароля; телефон опционально.
4. **Локализация** — базы с ПДн граждан РФ на территории РФ (ст. 18 п. 5 — трансграничка отдельно).
5. **Безопасность** — TLS, hash пароля, изоляция tenant, audit чтения ПДн (уже задел в PiiService).
6. **Права субъекта** — доступ, уточнение, удаление (право на забвение в рамках сервиса).

Пароль — **не** «ПДн в открытом виде»: храним только необратимый hash. Email — ПДн → схема `pii`.

Подтверждение почты — **рекомендация продукта** (меньше фейковых аккаунтов, проще восстановление), но не блокер запуска. Планируем отдельной фазой.

### Dual-write и 152-ФЗ
Копия в localStorage на устройстве пользователя — нормальна (данные у субъекта).  
Важно: не писать в LS чужие ПДн; после logout можно очищать кэш по политике (настраиваемо).

### Что считается ПДн в нашем синке
| Данные | ПДн? | Где |
|--------|------|-----|
| Email, ФИО | Да | `pii.user_profiles` |
| password_hash | секрет auth, не сырой ПДн | `users` |
| Названия проектов/папок | обычно нет | public |
| Поля мастера ИУЛ (шифр, объект) | бизнес | public JSONB |
| Фамилии в блоке подписей ИУЛ | могут быть ПДн третьих лиц | JSONB; минимизировать; не логировать |
| Картинка подписи (роспись) | биометрический/графический идентификатор — осторожно | S3 + метаданные; доступ только своей org |
| Исходный PDF чертежа | не синкаем | — |

## Acceptance (Клиент)

1. Регистрация без письма на почту, с галочкой согласия.
2. Создал проект ИУЛ на ПК‑A → вошёл на ПК‑B → дерево то же.
3. localStorage на обоих устройствах содержит дубликат после sync.
4. Исходный PDF после создания ИУЛ **не** появляется в S3/workspace API.
5. Чужой JWT не видит проекты другой org (тест изоляции).
6. VPS — только после отдельного «согласовано» + «да на прод».

## Границы волны W-35

**Входит:** spec, DDL, API snapshot + migrate-local, FE dual-write каркас, consent UI, политика MD.  
**Не входит в эту волну без доп. согласования:** боевой деплой на VPS, email-verify, полноценный GDPR-портал.
